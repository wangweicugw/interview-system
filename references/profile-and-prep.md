# 长期档案与下一场准备

## 状态

所有变更进入统一档案：

- `pending`：系统生成、尚未人工确认。
- `confirmed`：用户确认或补充过。
- `rejected`：保留历史，但不得作为有效依据。

系统不得把 pending 自动升级为 confirmed。修改通过追加修订实现，不抹掉旧版本。

## 答案版本

- 不同场次的同类问题可以自动提出归并，但不确定时分开保存。
- 每次回答新增版本，不覆盖旧版本；最新版本不自动成为推荐答案。
- 推荐答案依据事实准确、表达完整、真实经历证据和确认状态共同确定。
- 成熟答案保存 30 秒版、2 分钟版和追问展开。
- 缺少真实职责或数据时写“待补充”，不得编造。
- 多次同类回答归并后写入 `profile/standard-answers.json`，绑定真实场次与问题 ID；未经用户确认保持 `pending`。
- 归并时不是简单拼接：先提取各场稳定主线，再列出矛盾、缺口和未经核验数字；30 秒版只保留定位、主线和价值，2 分钟版再展开阶段、职责与结果，追问答案用于解释取舍和责任边界。
- 保存后运行 `check_standard_answers.py --root <data-root>`，通过后再重建题库。
- 高频统计分两层：主题频率只表示某领域被问及的场次；真实问法频率来自 `profile/question-clusters.json`，按相同面试意图人工或 AI 归并并绑定原题。AI 分组保持 `pending`，不得把关键词命中直接当作语义等价。
- 用户明确确认某份成熟答案后，运行 `set_standard_answer_status.py --root <data-root> --answer-id <id> --status confirmed --reason <原因>`；脚本追加 `profile/standard-answer-revisions.jsonl`，不能直接手改状态绕过修订记录。
- 独立待确认页 `interview-pending-review.html` 可离线排队 `standard_answer`、`question_cluster`、`question_cluster_create`、`profile_event` 和历史兼容的 `question_preference` 操作；自动生成的 `pending` 一律作为默认折叠的候选资料，不按固定配额制造人工待办；事实、个人贡献和简历风险候选也按需核对。AI 提醒、答案草稿和归并候选仍保留真实状态，不等于人工待确认任务。新页面不再展示或生成“练习偏好”控件；旧 `question-preferences.json` 仍被读取以维持历史排序/排除语义，历史记录不删除。题库和待确认页都可从原始题面手动创建待确认合并组。页面必须明确说明：确认高频问题是在确认组内原题是否询问同一核心问题，不是在确认答案。成熟答案是多场回答归并后的参考答法；长期档案项在页面上称为“AI 给你的复习提醒”，并说明它们是根据面试记录整理的复习、追问和简历表述提醒，不是已确认结论。每条提醒尽量同时显示原始问题、候选人现场回答和 AI 提醒；无法可靠定位时明确标注，不得编造。候选资料默认折叠并说明不影响练习，不能把所有 `pending` 都表述成必须立即确认的任务。练习区以用户现场回答、当前补充及现有参考稿生成可复制的 AI 改进请求，要求分清事实与建议；本地 HTML 不直接调用 AI。练习记录优先通过本机服务直接写入并显示“已入库 · 待审核”；服务不可连接时才下载单条 `practice_attempt` 待应用文件，并显示“已下载 · 未入库”。浏览器不能直接改写事实源；导出的 JSON 必须交给 `apply_review_actions.py`，它校验页面打开时的旧状态，防止用过期页面覆盖新修订。同机使用时，用户导出后只需在对话中说“应用刚导出的审核结果”，无需手工上传文件。
- 新场次导入后运行 `refresh_question_clusters.py`。默认只写 `profile/question-cluster-candidates.json`，不会自动增加页面上的同题组题数。逐条核对新场次的原题与已有题组；明显同一面试意图的题，即使相似分数为 `medium`，也用 `apply_review_actions.py` 将引用加入题组并记录前后快照。`--apply-high-confidence` 只追加高阈值候选，并把受影响聚类降回 `pending`；不能用词面相似度代替人工语义核对。应用后校验题组、审计答案并重建全部 HTML，核对页面题数。题组题数与成熟答案的来源题数是两种独立统计；未审阅的新回答不自动成为已确认答案的来源。
- 运行 `audit_standard_answers.py --reset-confirmed-stale` 对比聚类和成熟答案。新问题未被答案引用时，已确认答案回到待确认；现场回答中的数字只作为冲突线索，不自动判断真假。

## 历史分析

- 比较重复问题、知识状态变化、经常被深挖的项目和简历表述风险。
- 同一公司多轮单独形成趋势；不同岗位不直接比较总分。
- 面试结果只做相关性分析，不推断单一失败原因。
- 数据目录下的 `interview-history.html` 是统一入口：顶部只有“练习”和“历史面试”，首页一次只展示当前题组或单场题、对应的已保存参考答案及 AI 打磨入口；跨场题组展开后，各场原题和现场回答并列可比，草稿关联须核对。用户把满意的版本交回对话保存后，可在同页切到下一条练习主题；切题不等于已掌握。优先打磨高频题的完整答案，不要求做完全部题库或填写进度条；计时与自评仍是可选记录。历史场次可展开搜索。`interview-answers.html` 汇总全部跨场、逐题及延伸追问答案；`interview-question-bank.html` 是独立完整题库，原题和长尾题默认折叠；`interview-pending-review.html` 是按需核对入口。每场 `interview-review.html` 仍嵌入可搜索的历史列表，并链接总览与按需核对页。
- `rejected` 事件可供追溯但不得作为当前能力依据；`pending` 必须显示状态，不能与 `confirmed` 混用。

## 准备下一场

默认输出：

1. 新 JD 能力矩阵。
2. 可直接复用的 confirmed 成熟答案。
3. pending 或存在风险的答案。
4. 上一轮未覆盖的 JD 能力。
5. P0/P1 行动清单。
6. 预测性追问树，并明确标记为 AI 推测。

已有一场含 `jd-matrix.json` 的复盘后，可生成确定性准备简报：

```bash
<python> <skill-dir>/scripts/build_next_prep.py \
  --root <data-root> [--case <case_path>]
```

输出 `profile/next-interview-prep.md` 和同名 JSON。它按 `next_priority`、覆盖程度和表现状态整理重点，并只把 `confirmed` 资产列为可直接复用；`pending` 会保留状态，`rejected` 不作为当前能力依据。它不能替代新的 JD 分析，也不会生成通过率或因果判断。
Markdown 和 HTML 中的覆盖、表现、优先级与档案状态使用中文标签；JSON 保留稳定枚举值供校验与后续汇总使用。

用户指定目标公司并要求在本机服务查看时，每家公司使用一个 `profile/target-interview-preps/<slug>.json` 保存准备稿。问题必须标明 `招聘方参考题`、`历史原题`、`用户记忆转述` 或 `延伸练习题`；公司产品、价值观和岗位信息保存公开来源或“用户提供”说明。页面可显示未确认答案，但状态保持 `pending`，不得因此改写历史问答树或成熟答案状态。更新后重建全部 HTML，核对 `interview-preparations.html` 仅列公司入口、每家公司进入独立的 `interview-preparation-<slug>.html`，首页只保留“公司面试准备”入口和公司数量。

目标公司准备的完整取材、答案组织、写入和验收流程见 [company-prep.md](company-prep.md)。不要直接手改 JSON：先生成完整输入稿，再由 `upsert_target_interview_prep.py` 做重复检查、修订留痕和可选页面重建。

## 针对知识点继续追问

- 从真实题目、当场追问、逐题评分备注及 JD 要求定位一个具体知识点。先问一道，不一次给出整套答案；用户回答后再依据其实际回答追问原理、失效边界、证据或测试，直到能验证理解与落地能力。需要时可让用户运行 Java 代码和边界测试。
- 将问答树里已有的追问称为“问答树记录的追问”，并保留其证据限制；新编的问题称为“延伸练习题，非面试原话”。不要把自己构造的情境、数字、约束写成历史事实。
- 每轮反馈指出回答中已覆盖的点、尚缺的证据和下一道追问。技术事实不确定时先核验官方资料或明确保留待核验，不用猜测的标准答案给用户扣分。
- 用户希望离线自练时，把重点题的 `knowledge_point` 和 2–3 道递进 `followups` 存在私有 `profile/practice-focus.json`，按 [HTML 展示规则](html-presentation.md) 重建页面；原始问答树与逐字稿保持不变。
- 用户直接要答案时给出参考答法与适用前提；需要写入页面时只更新私有练习配置和派生 HTML，明确区分原始面试回答、AI 参考答案与官方技术依据。
- 题库卡可计时、记录脱稿回答和 1–5 自评。操作应用后，正文写入 `practice/private/`，元数据追加到 `practice/attempts.jsonl`；不得把自评当成掌握证明。
- 运行 `build_review_plan.py` 生成 `profile/review-plan.json` 和 Markdown。排序综合跨场频率、本场失分、JD 高优先级、是否到复习日和最近自评；页面显示的是复习建议和趋势快照，不跨岗位排名。

## AI 开发岗技术准备

### 先恢复证据，再出题

1. 先从 `qa-tree.json` 定位历史原题和当场回答；需要消歧时只读取最小范围的逐字稿片段。
2. 每道题标明来源：`历史原题`、`用户记忆转述` 或 `延伸练习题，非面试原话`。用户记忆与档案不一致时并列说明，不静默拼成一道题。
3. 对照 JD 建立能力缺口，但“使用过 AI 工具”不等于“有生产级 AI 应用落地经验”。个人职责、数据、事故和结果只能来自用户证据。
4. 技术结论按 [技术事实核验](fact-checking.md) 处理；产品当前能力和版本可能变化时，以当前官方资料为准。未经公开资料支持，不断言模型训练细节、隐藏提示词、私有检索策略或内部推理过程。

### 分层讲解

同一知识点按需给两个版本，保持事实一致：

- 30 秒面试版：先给定义和关系，再给一个关键边界。
- 2 分钟工程版：展开输入、模型、工具、状态、权限、执行环境、反馈循环、测试和人工确认。

解释 Agent 类概念时，优先使用以下边界：

- **模型**：根据上下文生成下一步内容或决策，不等于完整 Agent。
- **工具**：搜索、读写文件、执行命令、调用 API 等外部能力。
- **运行框架 / harness**：组织上下文、模型调用、工具调用、状态、终止条件和人工审批。
- **沙箱 / 执行环境**：命令与文件实际运行的受控边界，不等于模型本身。
- **Agent**：通常是模型、指令、工具、状态和循环组成的可行动系统，是系统范式。
- **ReAct**：把推理或决策、行动、观察结果交替推进的一类方法。它可用于 Agent，但不等于 Agent；不能仅凭产品表现就断言某产品严格实现论文版 ReAct。
- **Workflow**：步骤和分支主要由人预先定义；Agent 则让模型在边界内动态决定下一步。实际系统常是二者混合。

提到 Claude 或 Codex 时先消歧：Claude 可能指模型或聊天产品，Claude Code 才是编码代理产品；Codex 也可能因语境指模型、编码代理或产品能力。涉及当前产品行为时核对官方资料，不用名称替代架构说明。

### Coding Agent 标准答题骨架

用可观察的系统流程回答，不声称知道产品私有实现：

1. 用户给目标，系统加载指令和必要上下文。
2. 模型判断下一步是直接回答，还是请求搜索、读文件、改代码、执行命令等工具。
3. 运行框架检查权限和策略，在受控环境中执行工具。
4. 工具结果作为新观察返回，模型继续判断；达到终止条件后输出结果。
5. 高风险动作由人工确认，代码任务再以差异、测试、静态检查或运行结果验收。

不要把“整个仓库一次性塞进上下文”当成默认事实。更稳妥的表述是：系统通常按任务搜索和选择相关内容，并可能使用摘要或上下文压缩；具体检索、排序和压缩策略若无官方证据，应标为未核实。不要展示或索要隐藏思维链；面试中描述可观察的决策、行动、观察和校验循环即可。

### 递进追问树

围绕用户真实经历优先准备：

1. Agent 与普通聊天、代码补全、固定 Workflow 有什么区别？
2. ReAct 与 Agent 是什么关系？为什么不能画等号？
3. Coding Agent 如何选择工具、控制上下文并判断任务结束？
4. 为什么 AI 会生成可运行但错误的代码？如何通过评审、测试、权限和回滚降低风险？
5. RAG 文档如何切分、检索、重排和评估？哪些内容不适合只靠向量相似度？
6. 多模型接入如何统一协议、错误处理、限流、成本和可观测性？
7. 如果 AI 代码造成线上问题，个人责任、流程缺口和改进动作分别是什么？不得把责任推给工具。

### 输出与入档

准备简报中的 AI 题目至少包含：题目来源标签、证据状态、30 秒版、2 分钟版、可能追问、待补证据和技术依据。先按 JD 相关性与历史出现频率排 P0/P1，不机械凑固定题数。

可沉淀的成熟答案包括“AI 工具使用心得”“Coding Agent 原理”“Agent 与 ReAct 的关系”“AI 代码质量门禁”“RAG 切分与检索”“多模型接入”和“AI 事故复盘”。这些只是候选主题；必须绑定真实问题与个人证据，用户确认具体版本后才能标为 `confirmed`。
